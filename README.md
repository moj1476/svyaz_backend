# Backend «Связь»

## PostgreSQL и Prisma

Схемы находятся в `apps/<service>/prisma/schema.prisma`. Модели имеют имена
`Call`, `Message`, `Workspace`, а поля — `workspaceId`, `startedAt` и т. п.
Имена таблиц и столбцов PostgreSQL задаются через `@@map` и `@map`.

Для каждого SQL-сервиса хранится начальная миграция
`prisma/migrations/20261103000000_init/migration.sql`. История пересоздана для
пустых баз; совместимость со старой историей миграций больше не поддерживается.
SQL-файлы внутри Prisma остаются частью механизма миграций. CHECK-ограничения
содержатся в миграциях, поскольку текущие схемы Prisma не описывают их полностью.

```sh
pnpm infra:up
pnpm db:migrate
pnpm db:seed
pnpm build
pnpm start
```

В файле .env укажите LOCAL_USER_ID (UUID) и LOCAL_USER_LOGIN. Команда
db:seed создаёт настроенную локальную учётную запись, справочник разрешений
и индекс OpenSearch. Вариант db:seed:sql выполняет только шаги PostgreSQL.

При изменении схемы одного сервиса:

```sh
pnpm db:dev calls --name describe_change
pnpm prisma:generate
```

## Репозитории

`apps/<service>/src/infrastructure/postgres/` содержит явные вызовы
типизированного Prisma Client. В Messaging и Workspace `repository.ts` собирает
`state-loader.ts`, `command-selection.ts`, `state-writer.ts` и запросы из `queries/`. Массивов `tables`, динамического выбора моделей и
собственного описания соответствий столбцов больше нет.

`mapping.ts` преобразует представления значений: `Date` и `bigint` из Prisma —
в строки публичных контрактов и обратно. Также он собирает идентификаторы из
таблиц связей команд и ролей. Имена столбцов преобразует сама Prisma.

Общий `TransactionalRepository` координирует транзакцию, блокировку агрегата,
проверку ключа повторной команды и запись событий в outbox. Чтение и сохранение
состояния реализованы отдельно в каждом сервисе через конкретные модели Prisma.

Специализированные SQL-запросы сохранены для курсорной пагинации с точным
сравнением строк `COLLATE "C"` и обработкой пустых названий. Блокировки агрегатов
используют параметризованный PostgreSQL advisory lock через Prisma.

GraphQL API, `pnpm read` и `pnpm command` вызывают внутренние сервисы через gRPC.
Контракты находятся в `contracts/grpc/services.proto`. Контекст запроса, роли и
служебные запросы имеют поля protobuf. Команды, запросы и их результаты передают
действующие модели GraphQL в JSON-полях protobuf, сохраняя формат ID, Long и null.

## Межсервисное взаимодействие

- `pnpm start` запускает девять отдельных gRPC-процессов, затем GraphQL Gateway.
  Сервисы слушают loopback на последовательных портах от `GRPC_BASE_PORT` (по
  умолчанию 44051). Identity проверяет сессии, Workspace возвращает роли и
  членство. Messaging обращается к Workspace при проверке доступа к сообщениям.
- Изменение и его событие сохраняются в общей транзакции PostgreSQL. Kafka
  producer публикует outbox в `svyaz.domain-events.v1` и ставит отметку после
  подтверждения брокера. При сбое публикация повторяется. Ключ записи Kafka
  включает сервис-источник и ID агрегата.
- Search, Notifications и Audit используют отдельные consumer groups. Search
  запрашивает документ у Messaging по gRPC и обновляет OpenSearch. Notifications
  добавляет уведомления действующим получателям непрочитанных сообщений. Audit
  записывает события рабочих пространств. Повторная доставка учитывается по
  идентификатору события, уникальному получателю или ID документа.
- Недоступность синхронной зависимости и истечение gRPC-дедлайна возвращают
  `UNAVAILABLE`. Недоступность Kafka задерживает обновление поиска, уведомлений
  и аудита. После восстановления брокера обработка продолжается из outbox и
  сохранённых Kafka offsets. Некорректное событие фиксируется в журнале с
  разделом и смещением.

## Проверки

```sh
pnpm check
pnpm build
```

По указанию пользователя автоматические тесты удалены. До отдельного запроса
не добавляйте тесты, тестовые конфигурации и зависимости. Для проверки изменений
используйте форматирование, линтер, проверку типов и сборку.

## Локальный запуск

pnpm start открывает GraphQL на 127.0.0.1. Kafka по умолчанию доступна на 127.0.0.1:59092. При смене KAFKA_PORT укажите соответствующий адрес в KAFKA_BROKERS. Режим требует NODE_ENV=development
и использует настройки JWT из `.env`. После обновления запустите `pnpm db:migrate`,
чтобы применить миграцию учётных данных Identity. Локальная запись, созданная
`db:seed`, нужна командам разработки. `pnpm read <сервис>` и `pnpm command <сервис> <операция> <input.json>` используют запущенные gRPC-сервисы. Для входа через GraphQL зарегистрируйте
учётную запись с новым логином.

### Аутентификация GraphQL

В `.env` задайте `JWT_SECRET` (64 шестнадцатеричных символа) и
`AUTH_SESSION_TTL_SECONDS` (например, `3600`). Случайный секрет можно создать
командой:

```sh
node -p "require('node:crypto').randomBytes(32).toString('hex')"
```

Публичные мутации `register(input: RegisterInput!)` и
`login(input: LoginInput!)` возвращают `accessToken`, `sessionId`, `expiresAt`
и `viewer`. Все бизнес-операции и `viewer` требуют заголовок
`Authorization: Bearer <accessToken>`.

Auth Service проверяет подпись и срок JWT, наличие сессии в Redis, а также
статус учётной записи и сессии в PostgreSQL. По истечении TTL, после выхода
(`logout`) или отзыва сессии (`revokeSession`) требуется новый вход.
При недоступности Redis защищённые операции возвращают `UNAVAILABLE`.

Роли `OWNER`, `ADMIN`, `MEMBER` и `GUEST` назначаются в рамках рабочих
пространств. Зарегистрированный пользователь получает `OWNER` в созданном им
пространстве или роль из принятого приглашения. GraphQL передаёт идентификаторы
пользователя, сессии и его действующих ролей сервисам. Доступ к `auditEvents`
и `adminDashboard` определяется разрешениями, а управление участниками требует
`OWNER` или `ADMIN`.

`pnpm start:read` оставляет доступ к операциям аутентификации и бизнес-запросам
чтения.

## Организация кода

В `apps/graphql-api/src/` контекст запроса, кэш и загрузчики находятся в `context/`.
`application/composition.ts` координирует запросы и команды, `application/queries.ts`
направляет чтение в сервисы, `application/access.ts` проверяет доступ к объектам,
а `application/dashboard/` собирает сводку. Обработчики вложенных GraphQL-полей
разделены по областям в `presentation/resolvers/`.

В PostgreSQL-репозиториях Messaging и Workspace `state-loader.ts` загружает
состояние, `command-selection.ts` выбирает состояние и ключ блокировки для команды,
`state-writer.ts` сохраняет изменения, а `queries/` содержит списки, проверки
видимости и статистику. Вспомогательные функции записи получают тот же
`Prisma.TransactionClient`; транзакцией и блокировками продолжает управлять
`TransactionalRepository`.
